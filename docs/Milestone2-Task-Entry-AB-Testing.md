# Milestone 2: Task Entry A/B Testing Plan

## 1. Purpose

I want to explore whether making the task-entry process simpler would improve the TaskFlow experience. Before changing the current design, this plan outlines how I could compare two versions and decide which one works better.

## 2. The Problem

TaskFlow currently lets users type a task into an input field and select the **Add Task** button. This is a straightforward approach, but I still need to evaluate how easy it is to use.

The goal is to find out whether a small change to the task-entry experience could help users add tasks more quickly and with fewer mistakes.

## 3. Proposed Test

I would compare two versions of the task-entry interface:

- **Version A — Current design:** The existing input field and Add Task button.
- **Version B — Alternative design:** A more streamlined layout with a clearer visual focus on the input field and a more noticeable Add Task button.

Both versions would keep the same core functionality. The main difference would be the presentation of the task-entry controls.

## 4. Questions to Evaluate

The test would focus on three questions:

1. Can users add a task without needing extra instructions?
2. How long does it take users to enter and submit a task?
3. How often do users make an error, such as submitting an empty task or needing to try again?

## 5. Metrics

I would track the following measures for both versions:

- **Task-entry completion rate:** The percentage of attempts that successfully create a task.
- **Time to add a task:** The time between focusing on the input and successfully submitting a task.
- **Task-entry error rate:** The percentage of attempts that result in an error or require another attempt.
- **User feedback:** Short feedback from participants about which version feels easier to use.

These are proposed measurements. No user testing or data collection has been completed yet.

## 6. How I Would Run the Test

1. Prepare both versions of the task-entry interface.
2. Give participants the same task-creation instructions.
3. Have participants try each version under similar conditions.
4. Record completion, time, errors, and feedback.
5. Compare the results to see whether one version performs better.
6. Document the findings and decide whether the alternative design is worth keeping.

If enough participants are available, I would assign them to versions randomly or counterbalance the order to reduce the effect of practice. With a small sample, I would treat the findings as exploratory rather than conclusive.

## 7. Privacy and Limitations

The test should collect only the information needed to evaluate the interface. Participants should not be asked to enter sensitive personal information into test tasks.

The results could be affected by the number of participants, their familiarity with task-management applications, and the order in which they try each design. A preference for one design would not automatically prove that it is better for every user.

## 8. Expected Outcome

The goal is to use evidence rather than assumptions when deciding whether to change TaskFlow's task-entry interface. If the alternative design improves task completion or reduces errors without introducing new problems, I would consider adopting it. If the results are mixed, I would review the feedback and make further improvements before deciding.
